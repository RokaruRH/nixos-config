# План задачи

Задача: $ARGUMENTS

Исследование и план живут в репозитории, а не в контексте. Ничего не меняется, пока пользователь не прочитал план и не сказал начинать.

## Рабочая папка

- Корень — репозиторий, который задача меняет, а не тот, где запущен Claude: `git -C <путь внутри целевого репо> rev-parse --show-toplevel`
- Цель не в git-репозитории → спроси, куда писать
- Папка: `<root>/.ai/<nnn>__<slug>/`
- `<root>/.ai/.gitignore` с одной строкой `*` — создай, если нет; папка игнорирует сама себя и не коммитится
- `<nnn>` — три цифры, счёт вниз: первый план `999`, каждый следующий — наименьший существующий минус один; так новый всегда сверху
- `<slug>` — lowercase ASCII snake_case, до пяти слов; русское название — перевод, не транслит целиком: `unreal_mcp_setup`, `wine_berda_mouse`
- Возобновлённый план сохраняет номер

```
.ai/
  .gitignore
  999__unreal_mcp_setup/
    plan.md
    research/999__engine_plugin_paths.md
    notes/999__rejected_flatpak.md
```

- `plan.md` — единственный файл, который читает пользователь; заголовок — исходная формулировка задачи дословно
- `research/` — один вопрос на файл, у каждого утверждения доказательство: `path/to/file.nix:42`, вывод команды, URL официального источника
- `notes/` — остальное: решения по ходу, отвергнутые идеи, крайние случаи, ответы на ревью
- Файлы — `<nnn>__<slug>.md`, счёт вниз в каждой папке отдельно, одна тема на файл; папка появляется с первым файлом
- Больше ничего не создаётся — ни summary, ни картинок, ни скриптов, ни логов; вывод команд — выдержкой в заметку
- `plan.md` перечисляет каждый файл из `research/`, `notes/` и каждый `references/<scope>/README.md`; файл без ссылки из плана потерян

## Порядок

1. Найди корень, посмотри `.ai/`. Есть папка с подходящим slug → возобновление: прочитай `plan.md`, затем research и notes от новых к старым, продолжай. План без отмеченных пунктов ещё на ревью: выдай путь и остановись
2. Нет `plan.md` → создай папку; прочитай все `references/<scope>/README.md`, если есть
3. Пиши research по ходу исследования, а не после
4. Факты — по правилам фактчекинга из CLAUDE.md; Context7 — через скилл `context7-mcp`
5. Перед публикацией плана — самопроверка из CLAUDE.md
6. Напиши `plan.md`, выдай путь и короткое резюме, остановись

## Стоп

После появления `plan.md` ничего не меняется — ни правок, ни веток, ни коммитов, ни установок, ни `nixos-rebuild` — до команды: «начинай», «делай», «go», «делай шаг 1».

- Не команда: исходный запрос, одобрение («норм», «ок»), замечания по плану
- Замечания и команда в одном сообщении → обнови план, потом начинай
- Не уверен, команда ли это → спроси

## Ревью

После заголовка каждого шага — одна пустая строка, зона пользователя, затем `---`. Пользователь пишет туда что угодно; пустая зона — шаг принят. Claude в зоны не пишет. Чекбоксы — только прогресс Claude.

Каждый проход заканчивается остановкой:

1. Прочитай все непустые зоны и замечания в чате
2. Внеси их в `plan.md` и в research-файл, который они меняют — читать код можно, править нельзя
3. Вопрос («почему?», «объясни») = шаг неясен: перепиши шаг, в чате не отвечай
4. Замечание, требующее ответа пользователя → Открытый вопрос
5. Перенеси каждую зону дословно, с шагом и решением, в `notes/<nnn>__review_<n>.md`, очисти зону
6. Остальные изменения перечисли в чате

## После команды

- Перед первым шагом: `git status`; чужие незакоммиченные правки не трогай и не коммить
- Ветка — та, что в `plan.md`; не текущая → создай первой
- Один коммит на шаг сразу по готовности; файлы добавляй по путям, никогда `git add -A` / `git add .`
- Хук упал → чини, не `--no-verify`
- Не пушить без просьбы
- Шаг, требующий `sudo` (`nixos-rebuild switch` и т.п.), — команду запускает пользователь; дай её в синтаксисе Fish и жди результата
- Отмечай подшаги по готовности, затем шаг с коротким SHA: `### [x] 1. <шаг> — a1b2c3d`
- Отменённый шаг зачёркивается с причиной, не удаляется

## plan.md

Индекс, а не документ: каждая строка — действие или ссылка на файл с обоснованием. Ничего не повторяется дважды.

```markdown
# <исходная формулировка задачи> — план

## Открытые вопросы

- <выбор, варианты> — `research/999__engine_plugin_paths.md`

Ветка: `<branch>`

## Цель

- Один результат на строку, словами пользователя

## Подход

- <решение> — `research/998__mcp_transport.md`

## Шаги

### [ ] 1. <шаг>

---

- [ ] <действие> — `modules/apps.nix:42`

## Проверка

- <команда> — как выглядит успех

## Research

- `research/998__mcp_transport.md` — его вывод

## Заметки

- `notes/999__rejected_flatpak.md` — его решение
```

- Только эти разделы и только списки: без абзацев, без подзаголовков кроме шагов; допустим короткий `>` комментарий или блок кода с формой вызова
- Строка, переносящаяся трижды, → две строки или research-файл
- Открытые вопросы — всё нерешённое из любого файла, по строке; отвеченные уходят; нет вопросов → раздела нет
- Подшаг — одно действие и один путь, без обоснования — оно в research-файле, на который он ссылается; подшаг тестирования может перечислять несколько проверок
- Research и Заметки — каждый файл, от новых к старым, путь относительно `plan.md`, затем вывод, а не тема
- Чистое исследование — только Открытые вопросы, Цель (вопрос), Подход (ответ), Research, Заметки

## research/<nnn>__<slug>.md

```markdown
# <вопрос, который файл закрывает>

## Факты

- Утверждение — доказательство

## Ограничения

- Что должно соблюдать любое решение

## Варианты

### A — <название>

- Плюсы и минусы
```

Пустые разделы опускаются; нерешённое — в Открытые вопросы `plan.md`.
